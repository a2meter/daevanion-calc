# 데바니온 보드

다른 세션에서 이어서 작업할 때는 [인수인계서](HANDOFF.md)를 참고하십시오.

계산 결과의 점수는 옵션별 CP 측정 평균과 스킬 레벨별 값의 합계입니다. 실제 게임 전투력 산식을 구현한 것이 아니며, 이 점수의 최고값 검증이 실제 CP의 최고값을 보장하지 않습니다. 사용자가 힐피에 적용한 뒤 전투력이 약 998.9k에서 992.6k로 감소했다고 보고했으며, 이전 검증 당시 공식 API에서 992,629 CP와 709개 전량 사용을 확인했습니다. 실제 CP를 개선하는 산정 모형은 추가 측정과 검증이 필요합니다.

배포 주소: [데바니온 보드](https://daevanion.a2meter.workers.dev)

게임의 현재 상태는 링크로 가져옵니다. 데스크톱 프로그램 [데바니온 링크](link/README.md)가 게임 패킷에서 보드별 열린 노드와 스킬 레벨, 현재·최고 전투력을 읽고, **웹에서 재계산**을 누르면 이 페이지를 `<사이트>/#link=<데이터>` 주소로 엽니다. 주소의 `#` 뒤는 서버로 전송되지 않으며 페이지가 브라우저 안에서 해석합니다. 프로그램의 설치와 실행, 읽는 패킷, 페이로드 형식은 [link/README.md](link/README.md)에 있고 여기서는 다시 적지 않습니다.

페이지를 `#link=`가 든 주소로 열거나 열려 있는 페이지의 주소가 그렇게 바뀌면 다음 순서로 가져옵니다.

1. `assets/link-model.js`의 `decode`가 페이로드 버전 1을 읽습니다. 패딩 없는 base64url과 리틀 엔디언 값을 형식대로 해석하며, 표식(`DV`)·버전·길이가 맞지 않거나 보드·스킬 번호가 오름차순이 아닌 데이터는 받지 않습니다. `link/link_payload.py`의 `decode`와 같은 결과를 냅니다.
2. 네자칸·지켈·바이젤·트리니엘·루미엘(71~74, 79)의 열린 노드가 계산기의 원본 배치가 됩니다. 시작 노드는 비트와 관계없이 열린 것으로 보고, 실제 노드가 없는 자리의 비트와 그 밖의 보드(이 캐릭터의 75~78)는 쓰지 않습니다. 보드 완료 표시가 없거나, 다섯 보드 중 하나라도 링크에 없거나, 시작 노드와 이어지지 않은 열린 노드가 있거나, 소모량이 계산용 수량 837개를 넘으면 아무것도 가져오지 않고 이유를 화면에 표시합니다. 이때 이전 상태는 그대로이고 주소도 바꾸지 않습니다. 보드 번호는 직업마다 다르므로 이 다섯 번호를 쓰지 않는 직업의 링크는 가져오지 못합니다.
3. 스킬은 링크의 현재 레벨로 레벨별 값을 정합니다. 규칙은 아래의 스킬 레벨별 값 설명에 있습니다.
4. 가져온 링크를 브라우저의 `daevanion-link-import:v1` 키에 보관하고 주소에서 `#link=…`를 지웁니다. 새로고침해도 가져온 상태가 유지되며 다시 가져오지 않습니다. 화면 위쪽의 **게임 상태 가져오기**에 기준 시각, 현재·최고 전투력, 보드별 열린 노드 수, 레벨로 계산한 스킬 수를 표시합니다.
5. 지정해 둔 재계산 필수 노드를 유지한 채 전투력 재계산을 바로 시작합니다. 계산 시간은 입력칸의 값(기본 30초)입니다. 재계산 전의 화면은 가져온 배치 그대로이고, 변경 순서표는 가져온 배치에서 재계산 구성으로 가는 순서를 보여 줍니다.

보유 수량은 가져온 배치의 소모량으로 정합니다. 소모량 합계가 0개이거나 709개 이상이면 계산용 수량 837개를, 1~708개이면 그 합계를 사용합니다. 재계산은 루트 연결을 지키면서 계산용 수량을 모두 사용합니다.

가져온 상태의 편집과 재계산 결과는 `daevanion-planner:v2:link`, `daevanion-recalculated-plan:v1:link` 키에, 기본 상태의 것은 접미사가 없는 키에 따로 보관합니다. 옵션표의 측정값(`daevanion-option-measurements:v1`)은 두 상태가 함께 씁니다. 새 링크를 가져오면 편집 상태는 새로 가져온 배치로 시작하고 이전 재계산 결과는 지웁니다. **기본 상태로 돌아가기**를 누르면 가져온 상태와 그 편집·재계산 결과를 지우고 저장소의 기본 보드(`boards/*.json`)를 다시 표시합니다. 재계산 필수 노드는 두 경우 모두 유지하며, 방법은 아래의 재계산 필수 노드 설명에 있습니다. 보관된 링크를 읽을 수 없게 되면 지우고 기본 보드를 표시합니다.

캐릭터 검색은 제거했습니다. 검색 화면과 `assets/character-*.js`, 공식 캐릭터 API를 전달하던 Worker(`worker/index.mjs`)가 없어졌고, 페이지는 공식 API를 호출하지 않습니다. 검색으로 불러온 캐릭터의 저장본(`daevanion-character-session:v1`과 `…:character:<서버>:<캐릭터>` 키)은 더 읽지 않습니다. 마지막으로 불러온 캐릭터가 같은 보드(71~74, 79)를 쓰던 경우에 한해 그 캐릭터에 지정해 둔 필수 노드만 기본 상태로 한 번 옮기고 `daevanion-character-session:v1`을 지웁니다. 캐릭터별 편집·재계산 저장본은 읽지도 지우지도 않습니다.

루미엘의 신규 옵션 8종은 2026-11-11~12에 패킷으로 측정해 기록했습니다. 측정값이 없는 루미엘 옵션은 미측정으로 표시하고 합산 점수에서 제외한 채 재계산할 수 있습니다. 해당 옵션의 소모량과 연결 제약은 포함하며, 값을 입력하면 점수에 반영합니다. 희귀·전설 등급의 스탯에는 스킬 고정값을 적용하지 않습니다.

배포는 정적 파일만 제공하는 Cloudflare Worker입니다. `wrangler.jsonc`에는 `main`이 없고 `assets`만 있으며, 모든 요청에 `dist/`의 파일로 응답합니다. 공식 API 전달이 없어졌으므로 Worker 스크립트, `ASSETS` 바인딩, `/api/*` 우선 실행, 서울 리전 배치(`placement`), `global_fetch_strictly_public` 플래그를 설정에서 뺐습니다. 빌드 명령은 `npm run build`, 배포 명령은 `npm run deploy`이고 Worker 이름은 그대로 `daevanion`입니다. 계정 로그인 또는 기존 CI 인증 설정을 사용하며 코드에 인증 정보를 넣지 않습니다. `npm run build`는 `dist/`의 `assets`와 `boards`를 지우고 새로 복사하므로 프로젝트에서 없앤 파일이 이전 빌드에 남아 배포되지 않습니다.

```sh
npm ci
npm run build
npm run deploy
```

`main` 브랜치에 푸시하면 GitHub Actions(`.github/workflows/deploy.yml`)가 테스트와 빌드를 실행하고, 모두 통과하면 같은 명령으로 자동 배포합니다. Actions 탭에서 `main`을 선택해 수동으로 실행할 수도 있으며, 풀 리퀘스트에서는 테스트와 빌드만 실행합니다. 저장소 시크릿 `CLOUDFLARE_API_TOKEN`과 `CLOUDFLARE_ACCOUNT_ID`가 필요합니다. API 토큰은 Cloudflare의 `Edit Cloudflare Workers` 템플릿으로 만들며, 배포에 쓰는 권한은 그중 계정 범위의 Workers Scripts 편집입니다.

`npm run dev`는 검증용으로 같은 정적 파일을 8765번 포트에서 제공합니다. 데바니온 링크 프로그램의 사이트 주소를 `http://localhost:8765`로 바꾸면 로컬 페이지로 가져옵니다. 실제 사용에는 배포된 Cloudflare 주소만 필요합니다. 게시 없이 배포 구성을 검증하려면 `npx wrangler deploy --dry-run`을 실행하십시오.

`index.html`을 브라우저에서 열면 네자칸, 지켈, 바이젤, 트리니엘, 루미엘 탭 아래에 해당 HTML이 표시됩니다. 서버나 패키지 설치 없이 로컬 파일로 사용할 수 있습니다. 각 보드 HTML도 단독으로 열 수 있습니다.

| --- | --- | --- |
| 네자칸 · 71 | `boards/71.json` | `Nezkhan.html` |
| 지켈 · 72 | `boards/72.json` | `Zikel.html` |
| 바이젤 · 73 | `boards/73.json` | `Vaizel.html` |
| 트리니엘 · 74 | `boards/74.json` | `Triniel.html` |

원본 API 응답의 15×15 좌표와 노드 효과를 사용합니다. 처음에는 다섯 보드 JSON에서 `open: 1`인 노드를 활성 상태로 불러옵니다. 8행 8열은 활성화할 수 없는 루트이며, 상하좌우로 이어진 노드만 연결됩니다.

보유 데바니온 수량은 원본 API에서 활성화된 노드의 등급별 소모량을 합산해 자동 계산합니다. 현재 저장본은 네자칸 186개, 지켈 173개, 바이젤 183개, 트리니엘 167개로 총 709개입니다. 루미엘 저장본은 비어 있으며 다섯 보드는 계산용 수량 837개를 함께 사용합니다. 등급별 소모량은 일반 1개, 희귀 2개, 전설 3개, 특수 4개입니다. 저장본 원본 상태에서는 총 492개 노드가 활성 상태이며, 소모량은 709개, 잔여 수량은 128개입니다.

노드를 클릭한 뒤 F 키를 누르거나 상세 정보의 활성화 버튼을 누르면 현재 루트 연결 경로에서 가장 적은 노드를 추가하는 경로가 열립니다. 길이가 같으면 소모량이 적은 경로를 선택합니다. 경로 전체에 필요한 수량이 부족하면 아무 노드도 변경하지 않습니다. 효과와 잔여 수량은 활성 상태에 맞춰 계산됩니다. 불러온 원본의 활성 상태와 비교해 해제한 노드는 빨간 실선, 새로 활성화한 노드는 녹색 실선으로 표시합니다. 원본과 같아지면 색 테두리가 사라집니다. 잔여 데바니온이 0개이면 다음 연결 노드의 점선을 숨깁니다.

활성 노드를 선택한 뒤 F 키를 누르거나 상세 정보의 비활성화 버튼을 누르면 해당 노드를 해제할 수 있습니다. 해제로 인해 다른 활성 노드의 루트 연결이 끊긴다면 상태와 수량을 변경하지 않고 요청을 거부합니다. 다른 활성 경로로 루트와의 연결이 유지되는 경우에는 선택한 노드만 해제하고 해당 등급의 소모량을 반환합니다. 이 보드 초기화와 전체 초기화도 지원합니다. 확대와 축소, 맞춤 보기, 탭 방향키 이동을 지원합니다.

다섯 보드의 편집 상태는 브라우저의 `daevanion-planner:v2` 키로 보관됩니다. 이전 버전의 편집 상태 대신 원본 JSON 활성 상태로 한 번 시작하며, 이후에는 탭 이동과 새로고침 후에도 편집 상태가 유지됩니다. 보유 수량은 원본 활성 노드에서 계산하며, 원본 합계가 0개이거나 709개 이상이면 837개를 적용합니다. 이전에 저장된 수동 수량은 사용하지 않습니다. 원본 불러오기 버튼으로 다섯 보드의 JSON 상태를 다시 적용할 수 있고, 전체 초기화 버튼으로 모두 비활성화할 수 있습니다. 링크로 가져온 상태에서는 가져온 배치가 원본이고, 편집 상태는 `daevanion-planner:v2:link` 키에 보관됩니다. 실측 전투력 기록과 `boards/*.json`은 변경하지 않습니다. 브라우저마다 로컬 파일의 저장 정책이 다를 수 있으므로 일관된 사용 환경이 필요하면 같은 주소의 HTTP 서버로 열어 주십시오.

원본 `.daevanion__tab` 구성과 공식 노드 이미지를 참고했습니다. 이미지는 `assets/`에 저장되어 있어 화면을 열 때 외부 요청이 필요하지 않습니다. 캐릭터와 서버 번호는 `scripts/build_boards.py`에 지정되어 있으며, 데이터 수집에 쿠키나 인증 정보가 필요하지 않습니다. JSON은 수집 당시의 저장본입니다.

저장된 JSON으로 HTML과 탭 개수를 다시 생성하려면 다음 명령을 실행하십시오.

```sh
python3 scripts/build_boards.py
```

공식 API 데이터를 갱신하고 HTML도 다시 생성하려면 다음 명령을 실행하십시오. 네트워크 접근과 curl이 필요합니다.

```sh
python3 scripts/build_boards.py --refresh
```

하위 HTML을 직접 편집하는 대신 `scripts/board-template.html`, `scripts/resource-template.html`, `assets/board.js`, `assets/index.js`, `assets/planner.js`, `assets/styles.css`를 수정하십시오. 템플릿을 변경한 뒤에는 생성 명령을 다시 실행하십시오.

`index.html` 아래의 모든 보드 옵션표는 760개 노드를 등급, 이름, 효과가 같은 48종으로 합쳐 표시합니다. 분류별 옵션 수는 일반 6종, 희귀 14종, 전설 14종, 특수 14종입니다. 각 옵션의 노드 효과, 소모량, 다섯 보드별 등장 개수를 확인할 수 있습니다.

옵션표는 전투력 상승량이 큰 순서로 시작하며, 분류순과 소모량 대비순으로도 정렬할 수 있습니다. 효율은 입력한 전투력 상승량을 해당 노드 소모량으로 나눈 값입니다. 레벨별 값이 있는 스킬은 정렬과 효율에 그 값들의 평균을 씁니다. 연결 경로의 추가 비용이나 추가 노드의 효과는 합산하지 않습니다. 측정하지 않은 옵션은 임의로 추정하지 않으며, 0을 입력한 옵션은 전투력 상승이 없는 측정값으로 취급합니다. 정렬은 정렬 버튼을 누르거나 분류를 변경할 때 적용됩니다.

측정값은 편집 보드와 별도로 `daevanion-option-measurements:v1` 키에 보관합니다. 스킬 노드의 값은 등급이 아니라 도달하는 스킬 레벨로 정해지므로, 기본 캐릭터의 스킬 22종은 `boards/skill-values.json`의 레벨별 값을 씁니다. 옵션표에는 그 스킬의 노드를 하나씩 열 때마다 오르는 값을 `100 · 100 · 100 · 900`처럼 기본 레벨과 함께 표시하며 수정할 수 없습니다. 레벨별 값이 없는 스킬은 패시브 200 CP, 액티브 100 CP로 고정합니다. 링크로 가져온 상태에서는 스킬의 현재 레벨로 레벨별 값을 다시 정하고, 정할 수 없는 스킬만 고정값으로 둡니다. 고정값과 레벨별 값은 읽기 전용이며 측정값 초기화 이후에도 유지됩니다. 여러 번 잰 평균으로 기록한 옵션은 평균값으로 표시하고 입력칸에는 소수 첫째 자리까지 보여 주며, 계산에는 반올림하지 않은 값을 씁니다. 측정값 초기화는 보드 편집 상태에 영향을 주지 않으며, 같은 화면에서 초기화 되돌리기를 사용할 수 있습니다. 숫자가 완성되지 않았거나 유효하지 않은 동안에는 기존 측정값을 유지합니다. 옵션표 데이터인 `boards/options.js`도 보드 HTML 생성 명령으로 함께 갱신됩니다.

충격 해제의 12레벨 값과 집중의 기도의 13레벨 값은 직접 재지 못해 같은 등급의 다른 스킬 값으로 채웠습니다(`inferredLevels`). 네 노드를 모두 열면 스킬 22종의 합계는 22,000 CP이고, 이전의 등급별 고정값으로는 12,800 CP였습니다.

같은 파일의 `levels`는 등급별 레벨 전투력표입니다. 전설(액티브)과 희귀(패시브)마다 `[시작 레벨, 끝 레벨, 전투력, 관측 여부]` 구간이 1레벨부터 60레벨까지 빈틈없이 이어지며, 전투력은 스킬이 그 구간의 레벨에 도달할 때 오르는 CP입니다. 관측 여부가 `false`인 구간은 미관측입니다. 그 레벨에 도달하는 변화를 잰 적이 없어 이웃 구간의 값을 넣은 것이므로 실제 값과 다를 수 있습니다. 현재 미관측 구간은 전설 21~60레벨(200), 희귀 21~26레벨(200)과 32~60레벨(300)입니다. 전설 12레벨의 500은 한 번만 관측했습니다. 위 22종의 `values`는 모두 이 표에서 `baseLevel` 다음 레벨부터 읽은 값과 같으며, 보드 생성 명령이 이를 확인하고 다르면 멈춥니다.

링크로 가져온 상태에서는 이 표로 스킬마다 값을 다시 정합니다. `boards/skill-ids.json`이 스킬 옵션과 패킷의 스킬 번호를 잇습니다. 한 스킬에 번호가 여럿이면 `0000`으로 끝나는 기본 번호의 레벨을 쓰고, 링크에 기본 번호가 없을 때만 링크에 있는 가장 작은 번호의 레벨을 씁니다. 변형 번호에는 예전 값이 남을 수 있기 때문입니다. 링크의 현재 레벨이 L이고 가져온 배치에서 그 스킬의 노드가 c개 열려 있으면 기본 레벨은 L − c이고, j번째 노드의 값은 표의 (L − c + j)레벨 값입니다. 다음 경우에는 그 스킬에 등급별 고정값을 씁니다.

- 링크에 스킬 완료 표시가 없습니다(모든 스킬에 해당합니다).
- 번호표에 없는 스킬이거나, 링크에 그 스킬의 번호가 하나도 없습니다.
- L − c가 0보다 작습니다.
- 필요한 레벨이 표의 범위를 벗어납니다.

옵션표는 레벨로 계산한 스킬에 `레벨별 값`과 `100 · 100 · 100 · 900`, `기본 12레벨 · 현재 15레벨`을 표시합니다. 미관측 구간의 값을 쓰는 스킬에는 `미관측 21·22레벨`처럼 해당 레벨을 덧붙이고, 고정값으로 둔 스킬에는 이유를 표시합니다. 화면 위쪽의 가져오기 안내에도 레벨로 계산한 스킬 수, 고정값으로 둔 스킬 수와 이유, 미관측 구간을 쓰는 스킬 수가 나옵니다. 2026-11-13 캡처의 마지막 상태를 가져오면 22종의 기본 레벨이 모두 `baseLevel`과 같고 미관측 구간은 쓰이지 않습니다. 보드 생성 명령은 두 표를 `boards/skill-tables.js`(`window.DAEVANION_SKILL_TABLES`)로 내보냅니다.

아래는 2026-11-12까지의 단일 측정 기록에 대한 설명입니다. 기록은 `boards/measurements.json`에 남아 있지만, 같은 옵션에 평균 기록이 있으므로 계산값으로는 쓰지 않습니다. 이때의 값은 추가 공격력 +5가 439, 치명타 +10이 112, 추가 방어력 +50이 93, 치명타 피해 증폭 +5%가 2,460, 치명타 피해 내성 +5%가 1,218 등이었습니다.

치명타 저항 +10은 원본 기준 전투력 990,034에서 한 노드를 해제한 990,024와의 차이인 10 CP로 기록했습니다.

`scripts/optimize_board.py`는 이진 활성 변수와 루트 흐름 제약, 보드별 용량 및 연결 분리자 제약으로 공유 수량 문제를 계산합니다. 레벨별 값이 있는 스킬은 노드가 아니라 단계 변수에 값을 둡니다. j번째 단계는 그 스킬의 노드가 j개 이상 선택될 때만 켜지고 j번째 값을 받으므로, 16레벨이나 20레벨처럼 값이 뛰는 구간도 정확히 계산합니다. HiGHS에서 유효한 구성과 쌍대 상한을 함께 받아 검증하며, 모든 값이 정수일 때만 상한을 정수로 내림해 보관합니다. 기존 보드 구성은 연결과 총수량을 검증한 뒤 시작 후보로만 사용하며 검색을 제한하지 않습니다. 전체 검색은 120초를 사용하고, 최고값을 증명하지 못하면 이를 숨기지 않고 유효한 구성과 남은 상한을 보관합니다. 개별 보드 계산과 작은 그래프 검증은 최고값이 증명된 경우만 통과합니다.

`boards/all-optimization.json`은 모델 입력 해시, 활성 노드, 점수, 상한, 검증 상태를 보관합니다. 기본 생성 명령은 입력 해시·연결·수량·점수·상한이 맞는 결과를 재사용하므로 계산 라이브러리가 필요하지 않습니다. 해시에는 보드, 수량, 옵션별 값과 스킬 레벨별 값이 들어가므로 측정이나 보드가 바뀌면 저장본이 맞지 않게 되어 재계산합니다.

점수는 파이썬과 JS가 같은 순서로 더합니다. 보드는 네자칸·지켈·바이젤·트리니엘·루미엘 순서로, 보드 안에서는 노드 번호가 작은 순서로 더하고, 보드별 합계를 다시 같은 순서로 더해 전체 점수로 삼습니다. 레벨별 값이 있는 스킬은 이 순서에서 j번째로 선택된 노드에 j번째 값을 배정합니다. 재계산 구성과 원본 구성에 각각 따로 배정하므로 보드별 점수를 더하면 전체 점수와 정확히 같고, `boards/all-power-plan.json`의 수치는 `assets/optimizer.js`가 같은 구성에 대해 내는 수치와 마지막 자리까지 같습니다. 보드별 구성 내역에서 이런 스킬은 `basis: level`로 표시하며, 노드당 값은 그 보드의 노드에 배정된 값의 평균입니다. 어느 보드에 어떤 값이 배정되는지는 표시를 위한 약속이고, 전체 점수는 스킬별로 선택한 노드 수만으로 정해집니다.

저장본은 `scripts/solve_plan.cjs`로 다시 구합니다. 웹과 같은 `assets/optimizer.js`(개선 탐색과 HiGHS WebAssembly)를 Node.js에서 실행하며, 옵션별 값과 스킬 레벨별 값, 모형 해시는 `python3 scripts/build_boards.py --model`의 출력에서 받습니다. 이 출력은 파일을 쓰지 않고 표준 라이브러리만 사용합니다. 이전 저장본은 시작 구성으로만 쓰고, 모형이 같을 때만 이전 상한과 새 상한 중 낮은 값을 남깁니다. 계산 시간은 초 단위로 지정하며 기본값은 120초, 최대 600초입니다. 파이썬 실행 파일 이름이 `python3`가 아니면 `PYTHON` 환경 변수로 지정합니다. 이어서 보드 생성 명령이 저장본을 검증하고 모든 생성 파일을 다시 만듭니다.

상단의 전체 구성 적용 버튼은 다섯 보드를 한 번에 바꿉니다. 보드 탭에 따라 해당 배정과 원본 대비 스탯 비교표를 표시합니다. 전체 적용 이후 수동 편집은 자동으로 덮어쓰지 않습니다. 같은 페이지의 개별 구성 적용은 공유 구성의 해당 보드만 바꾸며 현재 잔여 수량이 부족하면 거부합니다. 비교표는 재계산한 구성의 저장본을 기준으로 하며 수동 편집을 따라 바뀌지 않습니다.

웹에서 옵션표의 전투력값을 수정한 뒤 **전투력 재계산** 또는 **수정값으로 전체 재계산**을 누르면 다섯 보드를 자동으로 다시 구성합니다. 계산 시간은 숫자 입력칸에 1~600초 사이의 정수로 직접 입력하거나 10·30·60·90·120초 프리셋으로 선택할 수 있으며, 기본값은 30초입니다. 계산 중에는 시간 입력과 프리셋을 잠급니다. 각 보드의 원래 사용량은 제한하지 않으며, 계산용 공용 수량을 정확히 사용하도록 합니다. 스킬의 레벨별 값과 고정값은 수정할 수 없으며 재계산에 그대로 씁니다. 루미엘 미입력 옵션은 합산 점수에서 제외하며, 기존 보드의 미입력 값이나 잘못된 값은 수정 후 재계산합니다.

재계산 결과에 반드시 넣을 노드는 **재계산 필수 노드**로 지정합니다. 보드에서 노드를 선택한 뒤 R 키나 상세 정보의 필수 지정 버튼을 누르거나, 옵션표의 재계산 필수 열에서 같은 옵션의 노드를 한 번에 지정합니다. 지정한 노드는 보드에 황색 모서리로 표시하고, 전체 구성 영역의 목록에서 하나씩 또는 모두 해제할 수 있습니다. 필수 지정은 재계산의 제약으로만 쓰며 수동 편집, 원본 불러오기, 초기화는 지정을 바꾸지 않습니다. 재계산은 필수 노드를 모두 포함하고, 루트까지 잇는 경로는 계산이 고릅니다. 필수 노드를 잇는 데 드는 최소 수량이 계산용 수량을 넘거나 조건을 만족하는 구성이 없으면 이유를 알리고 보드를 바꾸지 않습니다. 지정을 바꾸면 전투력값을 바꿨을 때와 같이 기존 결과의 적용 버튼을 잠그고 재계산을 요구합니다. 지정은 편집 상태와 같은 키의 `required` 항목에 보관합니다. 기본 상태는 `daevanion-planner:v2`, 링크로 가져온 상태는 `daevanion-planner:v2:link`입니다. 지정은 보드 배치가 아니라 사용자의 선택이므로 상태가 바뀔 때 함께 옮깁니다. 링크를 가져올 때는 그 순간 화면에 있던 상태(기본 상태, 또는 앞서 가져온 상태)의 지정을 새로 가져온 상태에 그대로 넣고, 기본 상태로 돌아갈 때는 가져온 상태의 지정으로 기본 상태의 지정을 바꿉니다. 그래서 미리 지정해 둔 노드는 가져온 직후의 자동 재계산에도, 이후에 가져오는 링크에도 그대로 적용됩니다.

`assets/optimizer.js`가 원본 노드와 현재 입력값으로 이진 활성 변수 및 보드별 루트 흐름 모형을 구성합니다. 필수 노드는 활성 변수의 하한을 1로 고정합니다. 스킬 레벨별 값은 `createProblem`의 `skills` 옵션으로 받아 파이썬과 같은 단계 변수로 모형에 넣고, 구성의 검증·요약·상한·최고값 재사용에는 모두 `score`가 계산한 정확한 점수를 씁니다. 경로 탐색과 교환 순서를 정하는 개선 탐색은 스킬 노드를 레벨별 값의 평균으로 어림하지만, 교환을 받아들일지는 정확한 점수로 정합니다. 레벨별 값은 `boards/skill-values.js`에서 읽고, 링크로 가져온 상태에서는 `assets/link-session.js`가 `boards/skill-tables.js`의 표로 만든 값으로 바꿉니다. 이 파일들은 `boards/measurements.js`와 함께 보드 생성 명령이 만듭니다. `assets/optimizer-worker.js`는 로컬에 포함한 `highs` 1.15.4 패키지의 WebAssembly 엔진을 별도 스레드에서 실행합니다. 화면을 막거나 외부 API·LLM을 호출하지 않습니다. 엔진의 [공식 API 문서](https://lovasoa.github.io/highs-js/docs/api/)와 라이선스는 `assets/vendor/highs/`에 안내했습니다. 웹 재계산에는 파이썬 설치가 필요하지 않으며, 워커와 바이너리를 불러오기 위해 로컬 HTTP 서버에서 페이지를 엽니다.

원본·현재 구성·이전 계산을 시작 후보로 사용합니다. 필수 노드가 빠졌거나 수량이 남는 후보는 버리지 않고 보정합니다. 필수 노드를 가장 싼 경로로 잇고, 수량이 넘치면 수량 대비 값이 낮은 끝 노드부터 내주고, 남으면 수량 대비 값이 큰 경로를 채웁니다. 이어서 개선 탐색이 노드 하나를 경로와 함께 더 넣고 값이 낮은 노드를 내주는 교환을 점수가 오르지 않을 때까지 반복합니다. 계산 시간의 처음 30%까지를 여기에 쓰고, 90%까지 HiGHS가 탐색하며, 남은 시간에 결과를 한 번 더 다듬습니다. 다섯 보드 크기에서는 HiGHS가 제한 시간 안에 시작 구성을 거의 개선하지 못하므로 점수는 주로 개선 탐색에서 나오고 HiGHS는 상한을 구합니다. 개선 탐색의 결과는 국소 최적이며 최고값을 보장하지 않습니다. 탐색 결과도 JS에서 별도로 연결·루트 제외·전체 비용·CP를 다시 확인한 뒤 다섯 보드를 함께 교체합니다. 취소하거나 입력·보드 상태가 계산 도중 바뀌거나 보관에 실패하면 계산 결과를 적용하지 않습니다. 계산 시간 내 최고값을 증명하지 못해도 검증된 구성을 적용하고 상한과 미확정 상태를 명시합니다. 최고값이 증명된 결과는 그래프·비용·수량·모든 CP가 완전히 같을 때만 재사용합니다.

재계산한 구성·비교표·다운로드 JSON은 같은 결과를 사용하며, 다음 방문 시에도 복원합니다. 전투력값이 바뀐 상태에서는 기존 결과가 현재 입력값과 다름을 안내하고, 재계산 전까지 이전 구성 적용 버튼을 비활성화합니다. 계산 완료 전의 수동 편집은 자동으로 덮어쓰지 않습니다.

검증은 다음과 같이 실행합니다. 작은 그래프의 전수 조사, 보드 사이 수량 재배분, 원자적 전체 적용, 잘못된 연결·수량 거부, 루트부터 이어지는 활성화 순서, 원본과 선택 효과의 독립 집계를 확인합니다. 레벨별 값은 `100 · 900 · 200 · 1000`처럼 오르내리는 값으로 전수 조사와 비교하고, 보드별 점수의 합이 전체 점수와 같은지, 저장된 구성의 점수가 파이썬과 JS에서 같은지도 확인합니다. 링크 가져오기는 `tests/link-import.test.cjs`가 확인합니다. `link/README.md`의 바이트 단위 예시와 잘못된 데이터의 거부, 배치 가져오기와 거부 사유, 레벨에서 값을 만드는 규칙, 필수 노드의 유지, 가져오지 않았을 때 기본 상태가 그대로인지를 봅니다.
