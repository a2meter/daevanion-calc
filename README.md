# 데바니온 보드

다른 세션에서 이어서 작업할 때는 [인수인계서](HANDOFF.md)를 참고하십시오.

계산 결과의 점수는 과거 노드별 CP 측정·추정·고정값의 합계입니다. 실제 게임 전투력 산식을 구현한 것이 아니며, 이 점수의 최고값 검증이 실제 CP의 최고값을 보장하지 않습니다. 사용자가 힐피에 적용한 뒤 전투력이 약 998.9k에서 992.6k로 감소했다고 보고했으며, 이전 검증 당시 공식 API에서 992,629 CP와 709개 전량 사용을 확인했습니다. 실제 CP를 개선하는 산정 모형은 추가 측정과 검증이 필요합니다.

배포 주소: [데바니온 보드](https://daevanion.a2meter.workers.dev)

캐릭터 검색은 **Cloudflare Workers + 정적 파일**로 배포합니다. 종족(천족 1 / 마족 2)과 해당 종족의 서버를 선택한 뒤 닉네임을 입력하고 검색하거나 Enter 키를 누릅니다. 검색창 아래에 프로필, 일치하는 이름 부분 강조, 서버를 표시합니다. 결과를 클릭하면 해당 캐릭터의 다섯 보드를 모두 불러와 화면에 적용합니다. 서버 목록은 제공된 42개 항목을 사용합니다.

공식 API는 외부 출처의 브라우저 호출을 CORS로 거부하므로 `worker/index.mjs`가 같은 도메인의 `/api/search/character`, `/api/character/info`, `/api/character/daevanion/detail` 세 경로만 전달합니다. 쿠키나 인증키가 필요하지 않으며 브라우저의 Origin·쿠키를 공식 서버에 전달하지 않습니다. 프로필 이미지는 공식 `profileimg.plaync.com`에서 불러옵니다. 정적 파일만 올리는 방식으로는 검색 API가 동작하지 않습니다.

보드 번호는 직업에 따라 다릅니다. 캐릭터 정보의 `daevanion.boardList`에서 네자칸·지켈·바이젤·트리니엘·루미엘의 실제 번호를 찾은 뒤 상세 API를 호출합니다. 예를 들어 호법성은 81~84번과 루미엘 89번이며, 상세 응답의 활성 개수가 목록과 일치하는지 확인합니다. 내부 화면 슬롯은 71~74번과 79번을 사용하고 실제 API 번호는 `sourceBoardId`로 보관합니다. 노드 번호와 활성 상태는 응답 그대로 유지합니다.

다섯 응답의 좌표, 노드 중복, 루트, 원본 연결을 모두 검증한 뒤 전환합니다. 실패하거나 다른 검색을 시작하면 이전 화면을 유지합니다. 보유 수량은 선택한 캐릭터의 원본 활성 노드에서 다시 계산합니다. 원본 소모량 합계가 0개이거나 709개 이상이면 계산용 수량 837개를 사용합니다. 1~708개이면 원본 합계를 사용합니다. 처음 활성 상태는 원본대로 불러오며, 재계산은 루트 연결을 지키면서 계산용 수량을 모두 사용합니다. 선택한 캐릭터와 보드 원본은 다음 방문에도 복원하고, 편집 및 재계산 결과는 캐릭터 번호와 서버 번호별로 분리합니다. 옵션표도 선택한 캐릭터에 맞추며, 다른 직업의 스킬은 패시브 200 CP·액티브 100 CP 고정 규칙을 적용합니다. 루미엘의 신규 옵션 8종은 2026-11-11~12에 패킷으로 측정해 기록했습니다. 측정값이 없는 옵션은 미측정으로 표시하고 합산 점수에서 제외한 채 재계산할 수 있습니다. 해당 옵션의 소모량과 연결 제약은 포함하며, 값을 입력하면 점수에 반영합니다. 희귀·전설 등급의 스탯에는 스킬 고정값을 적용하지 않습니다. 기존 네 보드에서 발견한 미측정 옵션은 입력 후 재계산합니다. 기존 캐릭터 저장본은 편집 상태를 유지하면서 실제 직업의 루미엘을 자동 조회하여 추가합니다. 기존 저장본의 최고값 증명을 새 캐릭터에 재사용하지 않습니다.

Cloudflare Workers 프로젝트에서 빌드 명령은 `npm run build`, 배포 명령은 `npm run deploy`입니다. 현재 Worker 이름은 `daevanion`입니다. 계정 로그인 또는 기존 CI 인증 설정을 사용하며 코드에 인증 정보를 넣지 않습니다. `wrangler.jsonc`의 서울 리전 배치(`aws:ap-northeast-2`)를 유지하십시오. 배포 검증에서 기본 미국 실행 위치는 공식 API에 404를 받았고, 서울 실행 위치(`cf-placement: remote-ICN`)에서는 검색과 보드 조회가 모두 200으로 응답했습니다. 이 설정은 Cloudflare 실행 위치를 지정하며 AWS 자원을 만들지 않습니다.

```sh
npm ci
npm run build
npm run deploy
```

`npm run dev`는 검증용으로 같은 Worker와 정적 파일을 실행합니다. 실제 사용에는 배포된 Cloudflare 주소만 필요합니다. 게시 없이 배포 구성을 검증하려면 `npx wrangler deploy --dry-run`을 실행하십시오.

`index.html`을 브라우저에서 열면 네자칸, 지켈, 바이젤, 트리니엘, 루미엘 탭 아래에 해당 HTML이 표시됩니다. 서버나 패키지 설치 없이 로컬 파일로 사용할 수 있습니다. 각 보드 HTML도 단독으로 열 수 있습니다.

| --- | --- | --- |
| 네자칸 · 71 | `boards/71.json` | `Nezkhan.html` |
| 지켈 · 72 | `boards/72.json` | `Zikel.html` |
| 바이젤 · 73 | `boards/73.json` | `Vaizel.html` |
| 트리니엘 · 74 | `boards/74.json` | `Triniel.html` |

원본 API 응답의 15×15 좌표와 노드 효과를 사용합니다. 처음에는 다섯 보드 JSON에서 `open: 1`인 노드를 활성 상태로 불러옵니다. 8행 8열은 활성화할 수 없는 루트이며, 상하좌우로 이어진 노드만 연결됩니다.

보유 데바니온 수량은 원본 API에서 활성화된 노드의 등급별 소모량을 합산해 자동 계산합니다. 현재 저장본은 네자칸 186개, 지켈 173개, 바이젤 183개, 트리니엘 167개로 총 709개입니다. 루미엘 저장본은 비어 있으며 다섯 보드는 계산용 수량 837개를 함께 사용합니다. 등급별 소모량은 일반 1개, 희귀 2개, 전설 3개, 특수 4개입니다. 저장본 원본 상태에서는 총 492개 노드가 활성 상태이며, 소모량은 709개, 잔여 수량은 128개입니다.

노드를 클릭한 뒤 F 키를 누르거나 상세 정보의 활성화 버튼을 누르면 현재 루트 연결 경로에서 가장 적은 노드를 추가하는 경로가 열립니다. 길이가 같으면 소모량이 적은 경로를 선택합니다. 경로 전체에 필요한 수량이 부족하면 아무 노드도 변경하지 않습니다. 효과와 잔여 수량은 활성 상태에 맞춰 계산됩니다. 불러온 원본의 활성 상태와 비교해 해제한 노드는 빨간 실선, 새로 활성화한 노드는 녹색 실선으로 표시합니다. 원본과 같아지면 색 테두리가 사라집니다. 잔여 데바니온이 0개이면 다음 연결 노드의 점선을 숨깁니다.

활성 노드를 선택한 뒤 F 키를 누르거나 상세 정보의 비활성화 버튼을 누르면 해당 노드를 해제할 수 있습니다. 해제로 인해 다른 활성 노드의 루트 연결이 끊긴다면 상태와 수량을 변경하지 않고 요청을 거부합니다. 다른 활성 경로로 루트와의 연결이 유지되는 경우에는 선택한 노드만 해제하고 해당 등급의 소모량을 반환합니다. 이 보드 초기화와 전체 초기화도 지원합니다. 확대와 축소, 맞춤 보기, 탭 방향키 이동을 지원합니다.

다섯 보드의 편집 상태는 브라우저의 `daevanion-planner:v2` 키로 보관됩니다. 이전 버전의 편집 상태 대신 원본 JSON 활성 상태로 한 번 시작하며, 이후에는 탭 이동과 새로고침 후에도 편집 상태가 유지됩니다. 보유 수량은 원본 활성 노드에서 계산하며, 원본 합계가 0개이거나 709개 이상이면 837개를 적용합니다. 이전에 저장된 수동 수량은 사용하지 않습니다. 원본 불러오기 버튼으로 다섯 보드의 JSON 상태를 다시 적용할 수 있고, 전체 초기화 버튼으로 모두 비활성화할 수 있습니다. 실측 전투력 기록과 `boards/*.json`은 변경하지 않습니다. 브라우저마다 로컬 파일의 저장 정책이 다를 수 있으므로 일관된 사용 환경이 필요하면 같은 주소의 HTTP 서버로 열어 주십시오.

원본 `.daevanion__tab` 구성과 공식 노드 이미지를 참고했습니다. 이미지는 `assets/`에 저장되어 있어 화면을 열 때 외부 요청이 필요하지 않습니다. 캐릭터와 서버 번호는 `scripts/build_boards.py`에 지정되어 있으며, 데이터 수집에 쿠키나 인증 정보가 필요하지 않습니다. JSON은 수집 당시의 저장본입니다.

저장된 JSON으로 HTML과 탭 개수를 다시 생성하려면 다음 명령을 실행하십시오.

```sh
python3 scripts/build_boards.py
```

공식 API 데이터를 갱신하고 HTML도 다시 생성하려면 다음 명령을 실행하십시오. 네트워크 접근과 curl이 필요합니다.

```sh
python3 scripts/build_boards.py --refresh
```

하위 HTML을 직접 편집하는 대신 `scripts/board-template.html`, `scripts/resource-template.html`, `assets/board.js`, `assets/index.js`, `assets/planner.js`, `assets/styles.css`를 수정하십시오. 템플릿을 변경한 뒤에는 생성 명령을 다시 실행하십시오.

`index.html` 아래의 모든 보드 옵션표는 760개 노드를 등급, 이름, 효과가 같은 48종으로 합쳐 표시합니다. 분류별 옵션 수는 일반 6종, 희귀 14종, 전설 14종, 특수 14종입니다. 각 옵션의 노드 효과, 소모량, 다섯 보드별 등장 개수를 확인할 수 있습니다.

옵션표는 전투력 상승량이 큰 순서로 시작하며, 분류순과 소모량 대비순으로도 정렬할 수 있습니다. 효율은 입력한 전투력 상승량을 해당 노드 소모량으로 나눈 값입니다. 연결 경로의 추가 비용이나 추가 노드의 효과는 합산하지 않습니다. 측정하지 않은 옵션은 임의로 추정하지 않으며, 0을 입력한 옵션은 전투력 상승이 없는 측정값으로 취급합니다. 정렬은 정렬 버튼을 누르거나 분류를 변경할 때 적용됩니다.

측정값은 편집 보드와 별도로 `daevanion-option-measurements:v1` 키에 보관합니다. 패시브 스킬은 전부 200 CP, 액티브 스킬은 전부 100 CP로 고정합니다. 고정값은 읽기 전용이며 측정값 초기화 이후에도 유지됩니다. 측정값 초기화는 보드 편집 상태에 영향을 주지 않으며, 같은 화면에서 초기화 되돌리기를 사용할 수 있습니다. 숫자가 완성되지 않았거나 유효하지 않은 동안에는 기존 측정값을 유지합니다. 옵션표 데이터인 `boards/options.js`도 보드 HTML 생성 명령으로 함께 갱신됩니다.

경로 탐색, 소모량, 옵션 집계와 전투력 효율 정렬 검증은 `node --test tests/*.test.cjs`로 실행할 수 있습니다.

사용자가 제공한 실측 기록은 `boards/measurements.json`에 기록합니다. 보드 생성 명령을 실행하면 해제 전후 전투력 차이를 노드 수로 나누어 옵션표에 반영할 데이터가 생성됩니다. 각 기록은 브라우저에 한 번 적용하며, 이후 사용자가 수정하거나 초기화한 측정값을 새로고침 시 덮어쓰지 않습니다. 새로운 기록은 해당 옵션에만 반영합니다.

각 해제의 CP는 직전 상태와의 차이로 계산합니다. 전체 복원 후 (1,1)과 (1,2)를 함께 해제한 총 감소량 4,489에서 공격력 +5의 기존 측정값 439를 제외하여 전투 속도를 4,050으로 추정했습니다. 치유력 강화를 해제한 상태에서 (15,2)와 (15,1)를 함께 해제한 총 감소량 843에서 방어력 +50의 기존 측정값 93을 제외하여 재시전 시간 감소를 750으로 추정했습니다. 복합 기록에는 `basis: inferred`와 `excludedPower`를 저장하며 화면에도 추정값으로 표시합니다. 좌표는 (col, row) 기준입니다.

치명타 저항 +10은 원본 기준 전투력 990,034에서 한 노드를 해제한 990,024와의 차이인 10 CP로 기록했습니다.

정신력 +50은 치명타 저항을 해제한 CP 990,024에서 추가한 990,038과의 차이인 14 CP입니다. 생명력 +100은 정신력을 다시 제거해 CP 990,024로 돌아간 뒤 추가한 990,048과의 차이인 24 CP입니다. 두 노드를 교체한 순변화 10 CP와 생명력 자체의 기여분 24 CP를 구분합니다.

등급별 스킬 고정값은 `boards/power-rules.json`에 보관합니다. 48종 중 패시브·액티브 22종은 고정값, 스탯 26종은 측정·추정값입니다. 치명타 피해 증폭은 990,048→987,149의 총 감소 2,899에서 추가 공격력 +5의 439를 제외한 2,460 CP입니다. 다단 히트 적중은 기존 복원 기준 990,048→988,833으로 1,215 CP, 미복원 상태의 저항 추가 988,833→988,923은 90 CP입니다.

루미엘 신규 스탯 8종은 2026-11-11~12에 같은 캐릭터로 노드를 하나씩 열고 닫으며 기록했습니다. 노드 열기·닫기 응답 패킷과 바로 뒤의 전투력 갱신 패킷을 짝지었고, 옵션마다 열기와 닫기의 변화량이 같았습니다. 철벽은 서로 다른 두 노드에서 같은 값이 나왔습니다. 기준 전투력이 약 994k~1,000k로 기존 기록(약 990k)과 다르므로, 값은 측정 당시 상태의 기여량입니다. 같은 세션에서 다른 상태로 다시 잰 공격력 증가는 5,917, 추가 공격력 +5는 442, 치명타 +10은 105로 기존 기록과 조금씩 달랐습니다. 측정 절차는 [실측 메모](NOTMETER_PACKET_NOTES.md)에 있습니다.

전투력 우선 구성은 공용 데바니온을 다섯 보드 사이에 재배분합니다. 각 보드의 루트 연결을 지키며 계산용 수량을 모두 사용하고, 한 번의 전체 적용으로 다섯 보드를 함께 교체합니다. 일부 보드가 원본보다 더 많은 수량을 쓰더라도 중간에 다른 보드 때문에 수량이 부족해지는 문제가 없습니다. 모든 검증을 통과한 뒤 상태를 교체하며 보관에 실패하면 이전 상태로 되돌립니다.

`scripts/prove_optimality.py`는 모든 루트 연결 구성에 필요한 정점 절단 부등식으로 원래 문제의 정수 완화 모형을 만들고, 연결되지 않은 후보를 발견하면 유효한 절단을 추가합니다. 보드별 예산은 고정하지 않습니다. 이 완화 문제의 최고 상한이 실제 연결 구성의 점수와 일치하므로 원래 문제의 최고값도 증명됩니다. 증거는 `boards/optimality-proof.json`, 검증 가능한 절단 9,425개는 `boards/optimality-proof.state.json`에 보관합니다. 최초 실행은 약 180초였으며, 저장한 모든 절단을 실제 그래프에서 다시 확인한 재실행도 약 13초 만에 같은 최고값을 확인했습니다. 캐시의 상한을 신뢰하지 않고 전체 노드 합에서 다시 시작합니다.

`scripts/optimize_board.py`는 이진 활성 변수와 루트 흐름 제약, 보드별 용량 및 연결 분리자 제약으로 공유 수량 문제를 계산합니다. HiGHS에서 유효한 구성과 쌍대 상한을 함께 받아 검증하며, 정수 전투력의 상한은 정수로 내림해 보관합니다. 기존 보드 구성은 연결과 총수량을 검증한 뒤 시작 후보로만 사용하며 검색을 제한하지 않습니다. 전체 검색은 120초를 사용하고, 최고값을 증명하지 못하면 이를 숨기지 않고 유효한 구성과 남은 상한을 보관합니다. 개별 보드 계산과 작은 그래프 검증은 최고값이 증명된 경우만 통과합니다.

`boards/all-optimization.json`은 모델 입력 해시, 활성 노드, 점수, 상한, 검증 상태를 보관합니다. 기본 생성 명령은 입력 해시·연결·수량·점수·상한이 맞는 결과를 재사용하므로 계산 라이브러리가 필요하지 않습니다. 측정이나 보드가 바뀌면 재계산합니다.

현재 저장본은 2026-11-13에 웹과 같은 `assets/optimizer.js`(개선 탐색과 HiGHS WebAssembly, 120초)로 구한 165,956점이며 상한은 166,339점입니다. 같은 모형을 파이썬 HiGHS만으로 120초 계산한 이전 저장본은 162,039점이었습니다. 파이썬 `--solve`에는 개선 탐색이 없습니다. 다만 저장된 보드별 구성을 시작 후보로 쓰고 그보다 낮은 결과로는 바꾸지 않습니다.

파이썬 재계산 환경은 다음과 같습니다.

```sh
python3 -m venv /tmp/daevanion-optimizer-env
/tmp/daevanion-optimizer-env/bin/python -m pip install -r scripts/requirements.txt
/tmp/daevanion-optimizer-env/bin/python scripts/build_boards.py --solve
```

보드별 데이터는 `boards/nezkhan-power-plan.json`, `boards/zikel-power-plan.json`, `boards/vaizel-power-plan.json`, `boards/triniel-power-plan.json`, `boards/lumiel-power-plan.json`이며 전체 결과는 `boards/all-power-plan.json`입니다. 각 보드의 수량은 공유 구성에서 배정된 값입니다. 이전 개별 계산의 `nezkhan-optimization.json`, `zikel-optimization.json`은 원본 수량 내에서 구한 과거 계산이며 현재 공유 구성은 `all-optimization.json`을 사용합니다.

상단의 전체 구성 적용 버튼은 다섯 보드를 한 번에 바꿉니다. 보드 탭에 따라 해당 배정과 원본 대비 스탯 비교표를 표시합니다. 전체 적용 이후 수동 편집은 자동으로 덮어쓰지 않습니다. 같은 페이지의 개별 구성 적용은 공유 구성의 해당 보드만 바꾸며 현재 잔여 수량이 부족하면 거부합니다. 비교표는 재계산한 구성의 저장본을 기준으로 하며 수동 편집을 따라 바뀌지 않습니다.

웹에서 옵션표의 전투력값을 수정한 뒤 **전투력 재계산** 또는 **수정값으로 전체 재계산**을 누르면 다섯 보드를 자동으로 다시 구성합니다. 계산 시간은 숫자 입력칸에 1~600초 사이의 정수로 직접 입력하거나 10·30·60·90·120초 프리셋으로 선택할 수 있으며, 기본값은 30초입니다. 계산 중에는 시간 입력과 프리셋을 잠급니다. 각 보드의 원래 사용량은 제한하지 않으며, 계산용 공용 수량을 정확히 사용하도록 합니다. 패시브 200 CP와 액티브 100 CP는 고정입니다. 루미엘 미입력 옵션은 합산 점수에서 제외하며, 기존 보드의 미입력 값이나 잘못된 값은 수정 후 재계산합니다.

재계산 결과에 반드시 넣을 노드는 **재계산 필수 노드**로 지정합니다. 보드에서 노드를 선택한 뒤 R 키나 상세 정보의 필수 지정 버튼을 누르거나, 옵션표의 재계산 필수 열에서 같은 옵션의 노드를 한 번에 지정합니다. 지정한 노드는 보드에 황색 모서리로 표시하고, 전체 구성 영역의 목록에서 하나씩 또는 모두 해제할 수 있습니다. 필수 지정은 재계산의 제약으로만 쓰며 수동 편집, 원본 불러오기, 초기화는 지정을 바꾸지 않습니다. 재계산은 필수 노드를 모두 포함하고, 루트까지 잇는 경로는 계산이 고릅니다. 필수 노드를 잇는 데 드는 최소 수량이 계산용 수량을 넘거나 조건을 만족하는 구성이 없으면 이유를 알리고 보드를 바꾸지 않습니다. 지정을 바꾸면 전투력값을 바꿨을 때와 같이 기존 결과의 적용 버튼을 잠그고 재계산을 요구합니다. 지정은 편집 상태와 같은 `daevanion-planner:v2` 키의 `required` 항목에 캐릭터별로 보관하며, 같은 캐릭터를 다시 불러와도 유지합니다.

`assets/optimizer.js`가 원본 노드와 현재 입력값으로 이진 활성 변수 및 보드별 루트 흐름 모형을 구성합니다. 필수 노드는 활성 변수의 하한을 1로 고정합니다. `assets/optimizer-worker.js`는 로컬에 포함한 `highs` 1.15.4 패키지의 WebAssembly 엔진을 별도 스레드에서 실행합니다. 화면을 막거나 외부 API·LLM을 호출하지 않습니다. 엔진의 [공식 API 문서](https://lovasoa.github.io/highs-js/docs/api/)와 라이선스는 `assets/vendor/highs/`에 안내했습니다. 웹 재계산에는 파이썬 설치가 필요하지 않으며, 워커와 바이너리를 불러오기 위해 로컬 HTTP 서버에서 페이지를 엽니다.

원본·현재 구성·이전 계산을 시작 후보로 사용합니다. 필수 노드가 빠졌거나 수량이 남는 후보는 버리지 않고 보정합니다. 필수 노드를 가장 싼 경로로 잇고, 수량이 넘치면 수량 대비 값이 낮은 끝 노드부터 내주고, 남으면 수량 대비 값이 큰 경로를 채웁니다. 이어서 개선 탐색이 노드 하나를 경로와 함께 더 넣고 값이 낮은 노드를 내주는 교환을 점수가 오르지 않을 때까지 반복합니다. 계산 시간의 처음 30%까지를 여기에 쓰고, 90%까지 HiGHS가 탐색하며, 남은 시간에 결과를 한 번 더 다듬습니다. 다섯 보드 크기에서는 HiGHS가 제한 시간 안에 시작 구성을 거의 개선하지 못하므로 점수는 주로 개선 탐색에서 나오고 HiGHS는 상한을 구합니다. 개선 탐색의 결과는 국소 최적이며 최고값을 보장하지 않습니다. 탐색 결과도 JS에서 별도로 연결·루트 제외·전체 비용·CP를 다시 확인한 뒤 다섯 보드를 함께 교체합니다. 취소하거나 입력·보드 상태가 계산 도중 바뀌거나 보관에 실패하면 계산 결과를 적용하지 않습니다. 계산 시간 내 최고값을 증명하지 못해도 검증된 구성을 적용하고 상한과 미확정 상태를 명시합니다. 최고값이 증명된 결과는 그래프·비용·수량·모든 CP가 완전히 같을 때만 재사용합니다.

재계산한 구성·비교표·다운로드 JSON은 같은 결과를 사용하며, 다음 방문 시에도 복원합니다. 전투력값이 바뀐 상태에서는 기존 결과가 현재 입력값과 다름을 안내하고, 재계산 전까지 이전 구성 적용 버튼을 비활성화합니다. 계산 완료 전의 수동 편집은 자동으로 덮어쓰지 않습니다.
